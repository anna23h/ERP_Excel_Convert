# 运单扫码回流

仓库打包时扫面单条码，收工导出「有货清单」，替代原来的**纸质勾选 + 手工转录**两步。

核心心智：**扫到 = 有货，清单内未扫到 = 无货。**

---

## 一、它在整个仓库里的位置

**它不是一条独立流水线**，而是 **VO 拉单流水线内部、阶段一与阶段二之间的一个可选替换段**。
它没有自己的数据源、也不产终态产出；上游吃阶段一的产出，下游喂阶段二的入口。
被它替换掉的是**两个人工步**（拣货员纸笔勾选 → 员工手工转录进 Excel），不是任何脚本。

```
                    ┌──────────────────── VO 拉单（vo_orders/）────────────────────┐
                    │                                                              │
   ERP + 天猫导出 ──▶│  阶段一 build_excel.py                                       │
                    │    ├─ 拣货表+面单.xlsx ─────────▶ 打印交仓库                   │
                    │    └─ …{店}{n}单 扫码清单.csv ┐ （同源同批，零新增人工步骤）    │
                    │                             │                                │
                    └─────────────────────────────┼────────────────────────────────┘
                                                  │ 拷到仓库机
                             ┌────────────────────▼───────────────────┐
                             │  扫码/扫码回流.html（本目录·可选）       │
                             │  载入清单作白名单 → 扫 LP → 导出        │
                             └────────────────────┬───────────────────┘
                                                  │ 有货清单{店}{n}单.csv
                    ┌─────────────────────────────┼────────────────────────────────┐
                    │  阶段二 stage2.py           ▼                                │
                    │    load_shipped_map ← GUI「有货订单清单」/ CLI --shipped      │
                    │    → 系统履约单号 / 发货表 / 账单上传 / 出库单                 │
                    └──────────────────────────────────────────────────────────────┘
```

**替代关系**：阶段二有两个互斥入口，二选一即可——

| 入口 | 代码 | 数据形态 | 谁产出 |
|---|---|---|---|
| 无货勾选返回（原流程） | `stage2.classify_return` | 逐 SKU 行 0/1 网格，空=未确认 | 仓库在打印件上勾 → 员工转录 |
| **有货订单清单（扫码走这条）** | `stage2.load_shipped_map` | 单号集合，一单一行 | 本工具导出 |

扫码天生是「有货集合」，所以走后者。**这条路径不进 0/1 裁决、不关心行结构**，因此多品订单多行不会触发原流程的「留空=未确认」报警（代价见下面的护栏一节）。

**与其它流水线的关系：没有关系。** `reorder/`（订货辅助）、`packing_list/`（出口箱单）、
`sales_insight/`（销售分析）、`vo_orders/fs_writeback.py`（FS 回写）、`po_reconcile/`（采购对账）
与本工具无任何数据或代码往来，改这里不会波及它们。

**技术上它是全仓的异类**，这也是它单独成目录的原因：

- 全仓唯一**非 Python** 交付物：单个 HTML 文件，零依赖、零安装、零 venv、零打包链。
- 全仓唯一跑在**仓库机浏览器**里的东西（其余全在办公室 Mac / Windows 上跑 Python）。
- 因此也是唯一**可以单独交付**的部分：把 `扫码回流.html` 一个文件发给同事即可，
  对方机器上不需要 Python、不需要这个仓库；每天的 `…{店}{n}单 扫码清单.csv`（文件名带当天日期）由跑阶段一的人发给他。

## 二、⚠ 上线前必读：护栏方向反转

原流程的护栏是「**任一留空即报警**」，防的是仓库漏返回导致误发。
改扫码后，未扫的单直接默认无货，**不会留空，该护栏自然失效**。

后果：**已寄出但漏扫的包裹会被判成缺货** → 天猫收不到回传、客户查不到物流、
并向后续统计注入假数据。而且它看起来与真实数据毫无差别，极难事后发现。

**必须用收工计数对账替代**：

- 扫码计数（顶栏「已扫 X / 总 Y」+「未知来源 Z」）↔ 交货代的实际箱数 / 取件回单件数。
- 对不上**当场查**，不要延后到第二天。
- 上线前几日与纸质勾选**并行**跑，收工双向对账，测漏扫率与噪音下报警音可闻性；数据稳定后再撤纸质。

### 分批清点：每 N 件停一次核对（把「收工清点」拆进扫描过程）

收工计数对账有个致命弱点：**就算做了、发现今天差 1 件，也不知道差在 400 件的哪一件**——回溯定位等于查不了，最后多半不了了之。分批清点就是来补这个的：

- **每扫满 N 件**（默认 **10**，底栏「分批清点 每 __ 件」可改、勾选框可关），跳出全屏浮层「清点这一批 · 应为 N 件」，把刚打包好的这一摞**当场数一遍**，再点「✓ 对上了」继续；数出来不对就点「⚠ 对不上」，差异**当场记下**，收工复核。浮层期间扫码暂停，专心清点。
- **价值不在「提前发现」，在「缩小范围」**：在第 k 个检查点发现对不上，要复核的只有刚才那 N 件，当场就能查出来，而不是收工时面对 400 件束手无策。
- 它也是目前唯一能触及**必发集之外**漏扫的机制：白天到货补发、他店混入——只要「包了没扫」，物理件数就会比扫描数多，下一个检查点必然暴露。
- 顶栏常驻「**本批 x/N**」（有对不上时追加「对不上 m」并高亮）+ 顶栏下方一条**分段进度条**（N 个格子，每扫一件亮一格，数亮格就是当前几件），不盯屏也能一眼看出离下次核对还差几件。
- 收工点「导出有货清单」时，若最后一批不足 N，会先弹一次**收尾清点**（应为剩余件数），点掉再真正导出；导出提示里汇总「分批清点 K 批，其中 m 批对不上」。检查点位置与记录随每扫存档，**刷新/降级后不重置**。

> ⚠ **物理前提（决定这套有没有意义）**：只有在「刚才那 N 件在物理上可数、可界定」时才成立——N 应等于打包后一个天然物理单元（周转箱 / 笼车格 / 一摞）的容量，核对动作 = 封箱前数一眼。若包裹一封箱就扔进笼车堆一起，就无从数「刚才那 N 件」，浮层会沦为**无脑点掉的噪音、反而制造假安全感**。**N=10 是与打包员讨论出的初值，仍需在真实场景核验**；不合适就在底栏调 N，或先关掉。
>
> **不替代收工计数对账**：分批清点在过程中缩小误差范围，收工计数对账仍是最终的全覆盖兜底，**两者都要**。

## 三、硬件要求

| 项 | 要求 | 原因 |
|---|---|---|
| 扫码枪后缀 | 必须配「回车(Enter)后缀」 | 页面靠 Enter 触发一次扫描判定 |
| 扫码枪模式 | 必须**实时传输**，禁用批处理/存储转发 | 存储转发下错误要等扫完回底座才暴露，等于没有即时反馈 |
| 面单遮挡 | 建议用硬纸板开窗，物理只露**顶部 LP 一维码** | 面单上还有 SF 号与二维码，从源头消灭误扫 |
| 声音 | 操作员离屏较远时建议外接音箱 | 声音是主要异常通道，不是屏幕 |
| 浏览器 | Chrome/Edge 直接打开本地文件即可 | 导出是**单个 zip**（不再逐份下载），无多文件拦截；若开了「下载前询问位置」只会问一次 |

USB HID 与蓝牙 HID 无线枪对浏览器行为一致，**换硬件零改动**。

## 四、一天怎么用

1. **载入清单**：点底栏「载入扫码清单」，选当天的 `…{店}{n}单 扫码清单.csv`（文件名带当天日期，别选成昨天的）。
   **可多选、可多次追加**——两店的清单可以一起载入，命中任一即通过；追加载入**不会清空**已扫记录。
2. **开扫**：扫面单顶部 LP 一维码，看颜色听声音即可，平时**不需要点任何按钮**。
   红色状态会一直挂着，直到下一次成功扫描才消失（方便抬头回看是哪单出了问题）。
   **唯一的例外是分批清点**：每扫满 N 件（默认 10）会弹浮层要你数一下刚才这一摞，点「对上了 / 对不上」再继续（详见第二节；不需要可在底栏关掉）。
3. **随时看顶栏**：`已扫 X / 总 Y 单`、`未知来源 Z`（Z>0 会高亮）、`本批 x/N` + 其下的**分段进度条**（每扫一件亮一格）、时钟。货代取件截止前用它判断进度。
4. **收工导出**：点「导出有货清单」，下载**一个** `有货清单打包_YYYY-MM-DD.zip`（内含各店有货清单 + 未知来源，一次下载，不再逐份弹框）。
5. **对账**：按第二节的口径核对计数，**解压** zip，把里面的 `有货清单{店}{n}单.csv` 发回办公室投阶段二。

底栏红色「清空」按钮是**彻底重来**：清白名单 + 已扫 + 未知来源 + 分批清点 + 本机今日存档，回到初始「载入清单」态（有二次确认；标红防误点）。**载错清单、要改载别的清单时用它**——因为白名单已入库、刷新会自动恢复，只有这一步能把错清单连同存档一并清掉；之后重新载入正确的 `…{店}{n}单 扫码清单.csv` 即可。（注：想重扫同一份清单也走这里，需重新载入该 CSV。）

### 四种反馈

| 情况 | 屏幕 | 声音 | 是否记录 |
|---|---|---|---|
| 清单内 + 首次 | 绿底「OK」+ 序号 + 订单号 | 短促清亮单音 | ✅ 记入有货 |
| 清单内 + 重复扫 | 红底「重复」 | 低沉三响报警（递降） | ❌ 拒绝（勿重复装箱）|
| LP 格式但不在任何已载入清单 | 黄底「未知来源·已记录」 | 上行双音 | ⚠ 记入**未知来源**，单独导出 |
| 不是 LP 格式（SF 号 / 订单号 / 二维码）| 红底「不是 LP 单号」 | 低沉三响报警（递降） | ❌ 拒绝 |

> **黄色「未知来源」为什么记录而不是拒绝**：实测确认打包时控不住按店串行，
> 且常把昨天没发出的包裹与今天批次一起寄走。硬拒会把本该一起发的隔日/他店包裹挡下。
> 所以改为记录、单独成文件、收工人工核对。**这个数要纳入收工对账口径。**

### 导出的文件（一个 zip，内含 n+1 份 CSV）

导出打包成**单个** `有货清单打包_YYYY-MM-DD.zip`（一次下载，规避 Chrome「下载多个文件」拦截——曾因未点允许**静默丢掉整店清单**）。解压后得到：

| 文件 | 内容 | 去向 |
|---|---|---|
| `有货清单{店}{n}单.csv` | 每个载入过的店各一份：`序号,Order Reference,VO Tracking No,店` | 投阶段二 GUI「有货订单清单」/ CLI `--shipped` |
| `未知来源运单{n}单.csv` | 仅一列 LP 单号（有未知来源时才产出）| **人工核对**，不投阶段二 |

未知来源文件即便误投阶段二也不会污染结果——阶段二按行找 `SCP` 开头的履约单号作连接键，
该文件只有 LP、没有 Order Reference，会被整行跳过。但仍应单独交人工。

zip 默认落浏览器下载目录（macOS `~/Downloads`）；用 Finder 双击 / Windows 资源管理器解压即可（文件名带 UTF-8 标记，中文不乱码）。

## 五、数据存在哪、什么时候能恢复

会话进行中，**数据源始终是内存**，导出也读内存——所以任何存储问题都**不会阻断扫码和导出**，
只影响「刷新/崩溃后能不能捞回来」。持久化是三层降级：

| 顶栏标识 | 状态 | 含义 |
|---|---|---|
| （不显示） | `localStorage` 正常 | 一切正常 |
| 黄「⚠备用存储」 | 已降级 IndexedDB | localStorage 写失败（多为配额满/无痕模式），已自动切备用；**收工务必导出** |
| 红「⚠仅内存·勿刷新」 | 两者皆失败 | 记录只在内存里。**切勿刷新或关闭页面，尽快导出** |

降级发生时会红屏 + 报警音提示一次，并在顶栏常驻标识（红屏会被下次扫描覆盖，常驻标不会）。

**误刷新后自动恢复**：白名单也随存档持久化，页面一打开就自动读回白名单 + 已扫 + 分批清点进度，
顶栏大字显示「已恢复今日」，导出/清空按钮自动可用——**不再需要手动重载清单**（继续扫即可）。
（历史：早期版本白名单不入库、恢复只在载入清单时触发，刷新后界面看着像空的、易误判数据丢失；已于 2026-08-10 改掉。）

自动恢复仍有两个前提，缺一不可：

1. 必须是**同一台机器、同一个浏览器**（数据在本机浏览器里，不上云、不跨设备）；
2. 必须是**同一天**（存档按日期分键）。

启动时会自动清理 30 天前的旧存档，无需人工维护。

> 已知边角：IndexedDB 写入是异步的，极端「写入途中断电」仍可能丢最后一单——
> 靠内存 + 收工计数对账兜底，未额外处理。

## 六、维护者信息

- **本目录只有 `扫码回流.html` 一个文件**，改动只需改它，仍须保持**单文件零依赖**（不引任何第三方库、不引外部字体/音频；声音用 WebAudio 合成）。
- 上游产出：`vo_orders/build_excel.py` 的 `build_scanlist` / `_write_scanlist`，在 `build()` 内按店循环、紧跟拣货表+面单产出，与之同源同批。列为 `序号 / Order Reference / VO Tracking No / 店`，编码 `utf-8-sig`（Excel 直接打开不乱码，浏览器端自行剥 BOM）。
- 下游消费：`vo_orders/stage2.py` 的 `_read_tables`（`.csv` → `pd.read_csv`，否则 `pd.read_excel`）+ `load_shipped_map`。入口高度模糊：不认列名/sheet，逐格找 `SCP\d+` 取后 15 位作连接键。
- 全链路 CSV 不用 xlsx：浏览器无法在不内联第三方库的前提下稳定产 xlsx，产 CSV 零成本。
- 设计与实施经过见 `docs/journal/`：**2026-07-21**（三块实现落地 + 走有货集合路径的决策）、**2026-07-22**（实测后改多选载入 + 名单外黄屏记录 + 导出 n+1 份）、**2026-07-26**（存储降级链 + 旧存档自动清理）、**2026-08-04**（分批清点：每 N 件停一次核对，点击确认 + 顶栏本批进度 + 收尾清点）、**2026-08-10**（白名单入库→刷新自动恢复；导出改单个 store-only zip 规避多文件拦截；「清空今日」升级为彻底清空含白名单+存档，作换清单逃生口）。
- 仓库全景与其它流水线见根 [README.md](../README.md)；全部入口与 CLI 参数见 [启动说明/运行指令.md](../启动说明/运行指令.md)。
