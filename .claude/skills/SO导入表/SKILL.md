# SO 导入表（Bestellung PDF → Odoo 销售单导入）

规则已于 2026-10-13 与用户定好，**写在脚本里**，不必再复述需求或逐条征求意见。
来龙去脉见私有库 `ISSUES.md` 的 `[SO 导入] A`。

## 第一步：直接跑

```bash
python3 -m so_import.so_from_pdf <Bestellung.pdf> <sale.order 模板.xlsx>
```

- 依赖 `pdfplumber`（不在主 requirements 里）：缺的话 `pip install -r requirements-pdf.txt`。
- 匹配走 Odoo API（只读，凭据同 `config.py` 的 `ODOO`）。**不要**改用用户附带的产品主数据 xlsx——
  快照会过期，2026-10-13 那份 13 个 PZN 里查不到 10 个，API 找回 8 个。
- 产出默认落 `output/YYYYMMDD/{SO号}_import_{PDF名}.xlsx`，同名自动加序号，不覆盖原件。

## 第二步：退出码 2 = 停下交给用户

脚本在这些情况下**不出表**，stderr 列出原因：

| 情况 | 交给用户的问题 |
|---|---|
| 某 PZN 在 Odoo 查不到 | 先去建档后重跑，还是这次剔掉这行？ |
| 某 PZN 命中多个产品（常见：单品 + `[2 Packs]` 组合装） | 用哪个外部 ID？ |
| 解析出 0 行 / 没有 Summe / 行合计 ≠ Summe | PDF 版式不认识——**如实说**，不要自己改正则硬凑 |
| 模板缺列、第 2 行头信息不全 | 让用户重新从 Odoo 导出模板 |

把异常行原样列给用户（PZN / PDF 名称 / 数量 / 各命中的外部 ID 与品名），**附上你的看法可以**
（比如「看名称应是单品」），**但决定必须等用户说**。拿到答复后带参数重跑：

```bash
python3 -m so_import.so_from_pdf B.pdf T.xlsx --exclude <PZN…> --pick <PZN=外部ID…>
```

查不到的 PZN，可以用 API 按 `pzn` 前缀或品名**查一下作诊断**（「系统里确实没有」还是「另有近似品」），
但查到的东西**只用于向用户报告，绝不写进表**。

## 第三步：交付

报这几样，脚本 stdout 里都有：

1. 产出路径（用户若要放到别处，复制过去，不要改脚本默认值）
2. **核对表**——PZN / PDF 名称 / 数量 / 净价 / ×1.19 / ERP 品名 / 可销售，整张贴给用户肉眼扫
3. 剔除了哪些行（若有），提醒建档后要手补进这张 SO
4. **合计核对**：全精度合计 vs Summe（减剔除行）的差额，并说明来源——对方系统按行先四舍五入到
   2 位再求和，差几厘是正常的，**不是匹配错误**；脚本逐行列出了每行的舍入差
5. `sale_ok=False` 警告（若有）：`Temp_` 临时品常见，建议导入前先在 Odoo 勾上可销售——
   本层只读，**不要尝试替用户改**

## 禁止项

- **不得用产品名做模糊匹配兜底**，哪怕名称看起来一模一样。
- **不替用户选**多命中里的哪一个，也不自行剔除行——`--exclude` / `--pick` 只能来自用户的答复。
- 不跳过异常行照常出表（脚本已拦；不要绕过，例如自己另写脚本出表）。
- `Unit Price` 不四舍五入（净价 × 1.19 全精度）；`Internal Reference` 留空。
- PDF 第 2 页起是条款正文，没有明细，脚本已自然忽略，不用特殊处理。
- 只支持目前这一家的 Bestellung 版式。遇到新版式先告诉用户，按项目规则立项后再扩展。
