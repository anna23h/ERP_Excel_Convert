# 采购成本核算

用户给一组销售单号要「采购成本」/「成本核算」。**`procure/po_price.py` 已经完全满足需求，
本流程不改任何代码。**要做对的是顺序和克制。

## 第一步：必须先问窗口，不许跳过

**收到需求后的第一个动作是提问：采购日期口径取多久？**

- 不许自己挑默认值（`--months` 默认是 3，在这个流程里**不作数**）
- 不许先跑一遍再问
- 不许一边问一边跑

窗口是业务判断：只有用户知道这批货大概什么时候进的。慢销品 3 个月根本覆盖不到。

用户会答「近一年」/「近半年」/「近 3 个月」这类。映射：

| 用户说 | `--months` |
|---|---|
| 近 3 个月 | 3 |
| 近半年 | 6 |
| 近一年 | 12 |
| 近 N 个月 | N |

## 第二步：跑脚本

```bash
python3 -m procure.po_price <单号…> --months <N>
```

**`--months` 必须显式写出来**，即便用户说的正好是 3 个月。命令里没有它，
就等于没问过——这是这条流程唯一的硬痕迹。

产出默认落 `output/YYYYMMDD/`，同名自动加序号，不会覆盖填过的旧表。
凭据走 `config.py` 的 `ODOO` 或环境变量 `ODOO_URL/DB/USER/API_KEY`。

**若中途改了窗口重跑，交付的必须是最后那次的产出。**
2026-09-27 踩过：拿 12 个月的数据算结论，交出去的却是 3 个月版的表，
表上查不到结论里的 `34×5.61`，被用户一眼看出。探索期产出可以落 scratchpad，
但一旦某次跑的数据进了结论，那一次的产出就是交付物。

## 第三步：交表，不加工

**只报两件事：**

1. 产出文件路径
2. 脚本 stdout 那几行摘要（每个产品的销售量 / 采购笔数 / 价区间）

唯一允许的额外一句：某产品**销售量 > 窗口内采购量**时说一声「可能需要更长窗口」。
**但不要自行加长重跑**——窗口始终是用户的决定。

## 禁止项（这些都是踩过的）

- **不要自己算成本分摊。** 「成本」列脚本一个字都不写，留空由人填，这是设计。
  同一产品窗口内常有好几个价，销售量要跨价分摊，人会写成 `70*4.63` 换行 `74*4.68`
  这种式子。既不是一个数、也不是任何一种平均，猜哪种都是错的。
- **不要出毛利、毛利率、加权均价。** 均价是结论不是事实，摆在证据表上只会诱导人照抄
  （初版有这一列，被用户删掉）。
- **不要额外查 picking / 发票**去核实发量、开票量。订购量与实发量确实会差
  （2026-09-27 实测有两个产品只发了订购量的八成左右，余量出库单已取消），
  但这由用户填成本时自己掌握，不在本流程内。
- **不要拆用户给的单号，也不要质疑它们该不该合。**
  **客户名称不同 ≠ 不同客户**：很可能是同一客户的不同法人实体，用户正因如此才把这几张单
  合并来问（2026-09-27 实测的两张单就是这种情况，具体是哪家见私有库 `ISSUES.md`）。
  跨单按产品合计是要的口径；`销售单` 列只留第一张**不是缺陷**，别去「修」它。
  （同族法人实体这个坑本项目栽过两次，另一次见 `common/vendor.NOISE_VENDOR_PATS`。）

## 本流程不需要立 issue

只是跑现成脚本，没有代码改动。「先立项再动手」针对的是改动。
