# 发票批量改价

用户要把一张**草稿**客户发票的单价整单改成某张价格表上的价。
**`procure/invoice_reprice.py` 已按用户定的口径做完全部逻辑，本流程不改代码、不临场写脚本、不连 Odoo。**

## 为什么绝不连 Odoo

用户账号的 API key 有**写权限**，`odoo_client` 的只读白名单只在本地拦，临时脚本绕得过去；
API 写入与界面操作在 Odoo 里记的是同一个 uid，事后分不清谁改的（2026-11-17 用户定，ISSUES `[发票改价] A`）。
所以这个流程**不 import `odoo_api`、不读 `config.py`、不跑任何 XML-RPC**——缺数据就请用户导出，不要自己去查。
导入也由用户在 Odoo 界面做，Claude 只出文件。

## 第一步：确认输入，然后直接跑 build

需要两份 Odoo「普通导出」（不勾导入兼容）的 xlsx，用户已各存了固定导出模板：

- 发票：客户发票列表勾**一张**草稿发票 → 导出。必需列：Status / ID（外部 ID）/ Invoice/Bill Date / Date /
  Partner / Untaxed Amount / Total / Invoice lines/ID / Display Type / Quantity / Unit Price / Discount (%) /
  Product/Internal Reference / Subtotal / Total / Label。
- 价格表：从价格表导出（条目作为子行），**一张**价格表。必需列：Product/Internal Reference / Fixed Price /
  Start Date / End Date（另有 Pricelist Name / Product/Name / Min. Quantity / Compute Price）。

文件齐了就直接跑，不必先问：

```bash
python3 -m procure.invoice_reprice build "<发票导出.xlsx>" "<价格表导出.xlsx>"
```

产出落 `output/YYYYMMDD/`：`发票改价_导入表_<id>.xlsx`、`发票改价_核对表_<id>.xlsx`、`发票改价_改前快照_<id>.xlsx`。

**退出码 2（`✗ …`）就停下，把原因原样交给用户**，常见几种：

| 报错 | 让用户做什么 |
|---|---|
| 发票状态不是草稿 | 在 Odoo 里先「重置为草稿」再导出 |
| 应当正好一张发票 / 一次只给一张价格表 | 只勾一张重新导出 |
| 导出里找不到「…」列 | 用固定导出模板重新导出（模板被改过或选错了） |

不要为了绕过报错去改输入文件或改脚本。

## 第二步：交表

1. 把终端里的 **Markdown 表原样贴出来**，再给三个文件路径（完整路径）。
2. 原样转达终端里的 ⚠ 提示（取价日退到记账日期、价格表名称里没有客户名等）。
3. **只就 ⚠ 行说明**；没有 ⚠ 就说「全部配上，按价格表改」。
4. 告诉用户下一步：在 Odoo **客户发票列表** → 导入「导入表」→ **先点「测试」**再导入；导入后用**同一个导出模板**再导出这张发票，把文件给你。

## ⚠ 怎么读（核对表「结果」「备注」列）

| 标记 | 意思 | 怎么跟用户说 |
|---|---|---|
| `配不上` | 价格表里没有这个**完整产品编码**（`_GW` 与非 GW 是不同产品，不互借） | 这行保持原价；问是不是价格表漏了这个品 |
| `无有效价` | 有这个编码，但取价日不在任何一条的起止日期内 | 保持原价；列出来请用户确认 |
| `多条有效` | 取价日有好几条价格都有效，已取 Start 最新一条 | 把「有效候选」列念给用户，请确认取得对不对 |
| `非固定价` | 价格表条目不是 Fixed Price | 保持原价；脚本不算公式价 |
| `无产品编码` | 发票行没有产品 | 保持原价 |
| 税率不为 0 的提示 | 这行挂了税，价格表价被**直接填进单价** | 请用户确认价格表价和这行「含税口径」列一致（本库销售价通常是含税价） |
| 口径无法判断 | Subtotal / Total 和 单价×数量 对不上 | 报出来，请用户看这行 |

## 第三步：导入后核对

用户给了改后导出就跑：

```bash
python3 -m procure.invoice_reprice verify "<改前快照.xlsx>" "<改后导出.xlsx>" --expect "<导入表.xlsx>"
```

- 退出码 0 →「除单价和由它重算的小计 / 合计外，没有别的字段变化」，原样转达即可。
- 退出码 2 → 把 ⚠ 列表原样交给用户，**不要猜原因、不要提议去 Odoo 里改回**——请用户自己看。
- 改前要用 build 产出的「改前快照」（或用户当时的原始导出），两份必须是同一个导出模板。

## 固定口径（2026-11-17 用户定，不许改）

- 按**完整产品编码**精确匹配，不按 PZN。
- 取价日 = 发票日期；草稿没填就用记账日期 `Date`。有效 = Start ≤ 取价日 ≤ End（空则不限）。
  多条有效取 Start 最新并标 ⚠；配不上 / 无有效价**保持原价**并标出。Min. Quantity 只显示，不参与取价。
- 含税口径不写死：逐行从 Subtotal / Total 反推；价格表价直接填 `price_unit`。
- **SO 单价不跟着改。**只改价格有变化的行；备注 / 分节行不进导入表。
- 导入表固定三列 `id` / `invoice_line_ids/id` / `invoice_line_ids/price_unit`，发票 ID 只写第一行
  （2026-11-17 在 47306 上实测导入成功）。

## 禁止项（2026-11-17 踩过或明确否决的）

- **不要连 Odoo**，哪怕只是「读一下确认」——请用户导出。
- **不要手改导入表或拼导入表**：原始导出直接改价再导回会因重复 `id` 列、带计算列而失败；改 `line_ids`
  的借贷会关掉发票自动补全、要手工凑平衡。只用脚本出的三列表。
- 不要替用户在多条候选价里挑价，不要把「配不上」的行按 PZN 或品名去凑价。
- 不要自己另写 scratchpad 脚本重算；口径以脚本为准，脚本不对就立 issue 改脚本。
