
**macOS 首次打开被拦**（提示"来自身份不明的开发者"）：右键点 `.command` → **打开** → 弹窗里再点"打开"。若双击变成用文本编辑器打开，是丢了可执行权限：


**拷到另一台 Mac**：复制 `vo_orders/`、`common/`、`requirements.txt` 和对应 `.command`（**不要拷 `.venv`、`raw_data/`**）。

**依赖按受众分三份**（2026-08-15）：`requirements.txt` 只有 `pandas`+`openpyxl`，是**启动器给同事装的最小集**（各条流水线依赖完全相同）；`requirements-dev.txt` = 最小集 + `pyinstaller`（打 exe 用）；`requirements-labels.txt` = `segno`/`reportlab`/`Pillow`（储位标签 `make_labels.py` 专用，按需单独装）。**别往 `requirements.txt` 加只有开发才用的包**——启动器会替同事装，装不上就是白挡人。

# 一、VO 拉单（VOTool 阶段一 / 阶段二）

```
导出当日 ERP + 天猫全量
        │
        ▼
[阶段一] vo_orders/build_excel.py ──► 拣货表+面单.xlsx ──► 打印给仓库
        │                                         │
        │                              仓库捡货、纸面标无货
        │                                         ▼
        │           办公室在「无货勾选」页把无货行填 1 另存；或用扫码回流出「有货清单」
        ▼
[阶段二] vo_orders/stage2.py（吃返回文件）──► B / C / D / E / 取消出库单
```

## 阶段一：生成「拣货表 + 面单」

```bash
python3 vo_orders/build_excel.py <erp[,erp2,...]> <完整天猫导出> [out.xlsx]
```

示例（多份 ERP 用**逗号**连接，不是空格）：

```bash
python3 vo_orders/build_excel.py raw_data/erpVO.xlsx,raw_data/erpGW.xlsx raw_data/天猫全量.xlsx
```

- **第二个参数是「完整天猫导出」**（全量、可跨多日，唯一天猫输入）。发货范围由程序二段式自动算出：`履约状态∈{新订单,商家已接单} ∧ 面单申请状态=已完成`，无需再单独导「面单已完成名单」。
- ERP 导出 **xlsx 或 csv 都可**，输出一致。
- 产出全部存到 `output/`，按店 `VO`/`GW` 各一份。

| 产出 | 内容 / 用途 | 何时跳过 |
|---|---|---|
| `YYYY年MM月DD日{店}{n}单 拣货表+面单.xlsx` | 三 sheet：`拣货表` / `面单`（打印给仓库）/ `无货勾选`（填 1 标无货） | — |
| `YYYY年MM月DD日{店}{n}单 扫码清单.csv` | 订单级白名单，与拣货表+面单同源同批 → 载入扫码 HTML（选用，见第七节） | — |
| `新订单获单清单{店}.xlsx` | `履约单状态=新订单` ∩ ERP 的系统履约单号 → 天猫后台批量获单 | 未传完整天猫导出 |
| `回传ERP销售上传表{店}.xlsx` | 取消 / 无运单 / 已补运单三类 Terms 写回**一张** → 上传 ERP | 无此三类订单 |
| `取消订单清单.xlsx` | 取消单种子表（**不分店**）。回传天猫后把后到的取消单手工补录进去，喂给阶段二生成取消出库单 | 当批无取消单 |
| `{店}补货预判清单.xlsx` | 今日需求 / 在手 / 缺口 + FS + Safety Stock + 采购画像 | **未传采购单导出**；或 ERP 导出没勾 `FS`/`Safety Stock`/`Supply Remark` 三列 |

> ⚠ **补货预判清单只有 GUI 有入口**：CLI 的第三个参数是输出路径，没有传采购单导出的位置（见 `build_excel.main()`）。要这张表就用 VOTool 阶段一的「采购单导出」（选填）栏。
> 它读的 `Safety Stock` 正是 `sales_insight` 回写进 ERP 的那个字段——两条流水线在这里接上。

- 打印格式已设：拣货表纵向压一页宽、面单横向、页脚「第 N 页，共 M 页」。

## 阶段二：仓库返回后

```bash
python3 vo_orders/stage2.py --mmdd <MMDD> --erp <ERP导出...> \
    [--shipped <有货清单...> | --nogoods <无货勾选返回...>] \
    [--tmall-full <完整天猫导出>] [--picking <出库原始数据...>] \
    [--cancel-list <取消订单清单...>] [--shipdate YYYYMMDD]
```

完整示例：

```bash
python3 vo_orders/stage2.py --mmdd 0611 \
    --erp raw_data/erpVO.xlsx raw_data/erpGW.xlsx \
    --shipped ~/Downloads/有货清单VO198单.csv \
    --picking raw_data/出库原始数据.xlsx \
    --cancel-list output/取消订单清单.xlsx
```

### 参数

| 参数 | 必填 | 说明 |
|---|---|---|
| `--erp` | ✅ | ERP 导出，**空格分隔可多份**（VO/GW 各一份）。货代合并模式除外 |
| `--mmdd` | 否 | 标签日期，默认今天，用于账单 D 的 `账单MMDD` 标签 |
| `--shipped` | 否 | **有货入口**（推荐）：真实发货订单清单，含履约单号/Order Reference 即可，可多份。吃 `.xlsx` 也吃 `.csv`（扫码回流导出的 zip 解压后，各店 `有货清单{店}{n}单.csv` 投这里） |
| `--nogoods` | 否 | **无货入口**：仓库返回的无货勾选文件，可多份。用它时需配 `--tmall-full` 算拣货候选 |
| `--tmall-full` | 否 | 完整天猫导出。无货入口算候选时必需；有货入口不需要 |
| `--picking` | 否 | 出库原始数据（stock picking 全量导出），可多份 → 出 `出库单.xlsx`（合并一张不分店）|
| `--cancel-list` | 否 | 取消订单清单（阶段一产出 + 人工补录后到的），**配 `--picking`** → 多出一张 `取消出库单.xlsx` |
| `--shipdate` | 否 | 发货日期 YYYYMMDD，默认今天 |
| `--billing` | 否 | **回落用**。ERP 导出含 `External ID` 列时账单直接由它生成；没有 ID 列才用这个喂账单模板导出 |
| `--forwarder` | 否 | 货代合并模式，见下（给了它其余参数忽略） |
| `--outdir` | 否 | 输出目录，默认 `output` |

`--shipped` 和 `--nogoods` 填其一即可（都填以有货为准）。

### 产出

| 产出 | 内容 |
|---|---|
| `系统履约单号.xlsx` (B) | 实际发货履约单号 → 上传天猫确认发货 |
| `发货表.xlsx` (C) | Order Reference + Tracking，GW / VO 分 sheet |
| `账单上传.xlsx` (D) | External ID + `账单MMDD` 标签 → ERP 开账单。**前提：ERP 导出含 `External ID` 列**，否则需 `--billing` |
| `出库单.xlsx` (E) | stock picking 过滤 + 统一发货日期，**合并一张不分店**（后缀 VO / GW / VO+GW 反映实际覆盖到的店）→ ERP 标记出库。需 `--picking` |
| `取消出库单.xlsx` | 取消订单的 picking，`Tracking Reference` 统一写 `订单取消`、不写 Carrier/ID、**合并一张不分店** → ERP 按此标记批量取消。需 `--picking` + `--cancel-list` |

各张独立，缺哪份输入就跳过哪张，不影响其他。

> **仅取消模式**：只带 `--cancel-list` + `--picking`（不给有货/无货清单）也能单独跑出取消出库单，便于收尾补跑；`--erp` 仍需带（作「别漏 ERP」护栏）。GUI 同理，「取消订单清单」为选填。

> ⚠ **`缺货记录.xlsx` 已从阶段二移除**，现在不产出了。未来单独成一个阶段（无货清单 × 库存 ERP 筛查），`build_shortage()` / `read_marked()` 作休眠代码保留（`stage2.py:356` 起）。

## 货代合并（跨店，收尾用）

```bash
python3 vo_orders/stage2.py --forwarder <发货表1> <发货表2> ... [--shipdate YYYYMMDD]
```

把当天各店、各次生成的「发货表」都传进来，去重合并。**产出两份**：

| 产出 | 内容 |
|---|---|
| `IHTCTGMBH+IH{YYYYMMDD}+{单数}.xlsx` | 给货代核对的合并清单（唯一跨店产出） |
| `YYYY年MM月DD日{n}单 天猫回执.xlsx` | 所有发货 Order Reference 后 15 位，各渠道合并去重 → 上传天猫做回执 |

运单冲突（同一 Order Reference 两个不同运单号）会在日志里报出，保留先出现的。

# 二、箱单（B2B 出口）

GUI：VOTool「箱单」标签页。CLI：

```bash
python3 packing_list/packing_list.py <sale.order.xlsx> [-o 输出目录] [--spare 2]
```

- 输入是 ERP 导出的 `sale.order` **行明细**。要几张 SO 合并成一张箱单，就在 ERP 里一次性导到同一份文件里，脚本按 `Order Reference` 自动分单。
- `--spare N`：每个 SKU 底下预留几行空行给仓库拆批次号/保质期（默认 2）。
- 产出照抄成品箱单排版：品名/SKU/条码/HS/原产国由脚本填；托盘号/批次号/箱号/箱规/箱数/保质期/毛重/尺寸/体积重留空给仓库手填；`Quantity total` 是公式 `=箱规×箱数`。
- 同名输出自动加序号，不覆盖。

# 八、采购数量与频次（指定供应商）

📖 详见 [../po_frequency/README.md](../po_frequency/README.md)（必需列清单、导出筛选建议、口径三条规则）。

把某供应商的 `purchase.order` 导出整理成「采购了哪些产品、各买几次、每次多少」的表。**纯整理不下结论**（与会议延伸出的分析无关）。纯 CLI，无双击入口、无 GUI。

```bash
python3 po_frequency/po_frequency.py <purchase.order.xlsx> [--vendor NAME] [--out PATH]
```

- 输入：`purchase.order` **行式导出**（Order Lines 粒度，订单头空行脚本自动 ffill）。
- `--vendor`：按供应商名过滤（子串、忽略大小写）；导出已单供应商时可省略。
- 产出：`output/<Vendor>_Purchase_Quantity_and_Frequency.xlsx`，两 sheet **英文表头**——`Summary`（每产品：频次/总量/每次均最大最小/首末采购/跨度/平均间隔，按频次降序）+ `Details`（逐笔：日期/单号/产品/编码/数量/单价）。
- 口径：订单头 ffill；SKU 归一（去 `x2/*2/_VO`）；频次 = 不同 `Order Reference` 去重。

# 九、库存周报（Odoo XML-RPC 只读拉数）

📖 详见 [../odoo_api/README.md](../odoo_api/README.md)（凭据、脚本账号要申请哪些读权限、launchd 部署、十条坑）。

把「销量排名 + 在手库存 + 安全库存」三合一，**直接从 Odoo 拉，不用手工导出**。纯 CLI，无双击入口、无 GUI。**只读，不写 ERP**——安全库存回写仍走上面第四节的人工导入表。

**先跑探针**（只读、不产文件，把字段名/仓库数/补货规则条数一次问清楚）：

```bash
python3 odoo_api/discover.py [--weeks 4] [--company-id N] [--timeout 180]
```

**正式周报**（推荐：带渠道过滤 + 接天猫处罚数据）：

```bash
python3 odoo_api/stock_report.py --since 2026-06-01 \
    --ref-contains VO,GW --violations 供应商违规数据.xlsx
```

全部参数：

```bash
python3 odoo_api/stock_report.py [--weeks 12 | --since YYYY-MM-DD --until YYYY-MM-DD] \
    [--peak-cover 1.0] \
    [--states sale,done] [--ref-contains VO,GW] [--ref-excludes S0] \
    [--violations 违规数据.xlsx] [--violation-since YYYY-MM-DD] \
    [--exclude-vendor "供应商名"] [--by-warehouse] [--orderpoint-agg sum|max] \
    [--company-id N] [--external-id] [--csv-only] [-o 输出目录] [--timeout 180]
```

| 产出（默认 `output/YYYYMMDD/`） | 内容 |
|---|---|
| `库存周报.xlsx` / `库存周报.csv` | 全 SKU 按销量降序：排名 / 累计占比(ABC) / 销量 / 周均销量 / 下单次数 / 销售额 / **在手 / 实物库存 / 已预留 / 可用 / 在途入库 / 待出库 / 预测库存** / **两路安全库存并列** / 取用值 / **缺口(按在手) / 预测缺口(按预测)** / 可撑周数 / **套件** / 在售 / 产品ID |
| `安全库存不一致.csv` | 两路**真正冲突**的行（都有但不等 / 只有补货规则）。「只有产品字段」不进表——B 侧没在用时那是常态，只报计数 |
| `安全库存待配清单.csv` | **有销量但两路都没配安全库存**的 SKU，按销量降序 |
| `缺货违规风险清单.csv` | 给了 `--violations` 才产。因缺货被天猫罚过的 SKU，「被罚过·未配安全库存」排最前、按罚款降序，带峰值列。**最该先看这张** |

- **⚠ 需求是尖峰型的，别只看周均**。实测（6 月至今 12 周，样本 170 个有量 SKU）峰值周/周均**中位数 2.38×**、76% 的 SKU ≥2×；**86 个按周均看「能撑 ≥2 周」的 SKU 里，30 个连一个高峰周都接不住**——而罚款恰恰发生在峰值那一周。看 `可撑峰值周数` 和 `峰值缺口` 两列，别只看 `可撑周数`。`--peak-cover N` 决定要备够接住几个峰值周（默认 1）。
- **窗口默认 12 周，别调回 4**。4 周是 2026-08-01 为「均值推算安全库存」定的口径（那结论仍成立），但峰值识别需要更长窗口，4 个数据点看不出尖峰。`--violation-since` 不给时自动跟随销量窗口起点。
- **⚠ 这条流水线的目标是降低天猫因缺货产生的处罚**，不是做销量排名。`--violations` 传天猫后台导出的「供应商违规数据」，报表就按**真实罚款**排优先级。2026-08-23 首测：缺货类违规占 14.3% 的单数但 **54.7% 的罚款**，涉及 529 个 SKU，其中 **449 个（86%）至今没配安全库存**（2,294 EUR / 754 单）。
- **「晚于应发货时间」不算缺货类**（虽然它占 75% 的单数）：没有历史库存快照就分不清是缺货还是仓库作业慢，硬归因会把仓库效率问题伪装成库存问题。缺货类只认四种：商家毁单×2 + 晚于考核商家缺货时间 + 晚于平台判定缺货时间。
- **⚠ 渠道口径必须显式给**。不加 `--ref-contains` 时销量是**全渠道**，会被 B 端整箱单主导：2026-08-23 实测 B 端（`S0` 开头）只占 378 行订单却占 **90% 的件数**，而安全库存是给天猫 C 端维护的。同一窗口「销量前 50 名里配了安全库存的」，全渠道算 3 个、C 端算 **45 个**——口径混用会导向完全相反的结论。带 `--ref-contains` 时并列多出 `销量_其它渠道` / `销量_全渠道` 两列；`可撑周数` 一律按全渠道算（库存被所有渠道一起消耗）。launchd plist 已默认带上。
- **`sale.report` 是实时视图不是快照**：同一历史窗口过些天再拉数字会变（实测窗口内 4.9% 的已确认单在导出后被改动过）。**周报不可事后复现，要留证据就留产出文件。**
- **与手工导出对拍已通过**（2026-08-23）：安全库存 62 个运营人工值 59 个与 ERP 现值完全相等；销量 567 个共有 SKU 中 324 个完全一致、差异中位数 0；排名 Spearman 0.913，前 20 名重叠 19/20。详见 [odoo_api/README.md](../odoo_api/README.md)。
- **凭据**：环境变量 `ODOO_URL`/`ODOO_DB`/`ODOO_USER`/`ODOO_API_KEY`，或 `config.py` 里的 `ODOO = {...}`（模板见 `config.example.py`，已 gitignore）。用 **API Key** 不用登录密码。
- **两路安全库存**：A = 产品主数据上的自定义 `Safety Stock` 字段（`sales_insight` 回写、补货预判清单读的就是它）；B = `stock.warehouse.orderpoint.product_min_qty`（Odoo 标准补货规则，滤掉 `trigger=manual` 的临时建议；该字段 Odoo 14 就有，实测 5 条里 4 条是 manual）。缺口按 A 算，A 空退回 B。
- **⚠ 在手库存用 `qty_available` 不用 `stock.quant` 汇总**。组合装（`x2`/`_GW`）是 phantom BoM 套件，没有自己的实物库存、quant 上恒为 0，只有 `qty_available` 会从组件推算（基础款 106 → `x2` 显示 53）。2026-08-23 实测 560 个套件里 557 个 quant 为 0，改口径后「低于安全库存」从 97 → **59 个，38 个是套件造成的假警报**。报表另出 `实物库存`（quant 原值）与 `套件` 两列；`已预留`/按仓拆列仍来自 quant，套件行是 0。**在手列不可跨行求和**——套件与其基础款是同一批实物。
- **⚠ 在途/预测要剔掉不会真收货的技术性采购单**。并非所有确认状态的采购单都会真的收货——某些系统集成会用 PO 建技术性映射，这类单永远不到货，却在 Odoo 里是确认状态、会生成未完成入库 move。2026-08-23 实测**全局 7460 条未完成入库里 7350 条（98.5%）来自单一供应商的这类单**，真实在途只有 105 条 / 88 个产品。哪些供应商属于此类是业务知识，配在 `config.py` 的 `ODOO_EXCLUDE_VENDORS`，或用 `--exclude-vendor "名字"` 覆盖。排除后 `在途入库`/`待出库`/`预测库存`/`预测缺口` 四列才可用：**按在手算 59 个 SKU 低于安全库存，按预测算 75 个**——两个口径都留着，问的是不同的问题。
- **产品范围是并集**：`sale_ok=True ∪ 有销量 ∪ 有库存 ∪ 有补货规则`。只按 `sale_ok` 会漏掉「已下架但仍在卖」的货，报表用 `在售` 列标出来。
- **定时**：`odoo_api/run_weekly.sh` + `odoo_api/com.ihtct.stockreport.plist`（launchd，每周一 08:30）。用 launchd 不用 cron——到点机器睡着了 launchd 会唤醒后补跑，cron 直接跳过。
- 构造数据自测（不连 ERP）：`python3 odoo_api/test_stock_report.py`。
