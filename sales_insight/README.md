# sales_insight — 销售分析 + 安全库存提醒 + Safety Stock 回写

## 为什么有这条流水线

运营同事在 Excel 里手工维护安全库存；而 **ERP 产品主数据里本来就有 `Safety Stock` 字段，
`vo_orders/build_excel.py` 的「补货预判清单」已经在读它**（连同 `Quantity On Hand` 和 `FS`）。
两边完全断开——运营的判断进不了 ERP，拉单流程拿到的是过期或空的安全库存。

这条流水线把三份数据合一，产出排名与提醒，并**把安全库存写回 ERP**，让已有的补货预判
清单自动拿到正确值。两条流水线就接上了。

## 这个目录里有两个脚本，别用错

| | `sales_insight.py` | `safety_writeback.py` |
|---|---|---|
| 干什么 | 销售分析（排名 / 提醒 / 推算候选值），回写只是副产品之一 | **只干回写这一件事** |
| 需要销售数据 | ✅ 必需 | ❌ 不需要 |
| SKU 全集由谁定 | **销售导出**（安全库存表里有、销售导出里没有的 SKU 会被丢掉） | **安全库存表**（表里有几个就写几个） |
| 写 `Supply Remark` | 写（运营备注前置成 `YYYYMMDD:安全库存 …` 段） | **不写**（该列整个不出现） |
| 什么时候用 | 要看销量排名 / 补货提醒 / 给运营出推算候选值 | 运营发来一张「这些货配多少」的表，只想把值写进 ERP |

判断标准很简单：**你关心销量吗？** 不关心就用 `safety_writeback.py`。

2026-09-22 实测过一次反面案例：运营发来 52 个 SKU 的 `15天安全库存`，没有销售数据，
为了跑通 `sales_insight.py` 得伪造一份零销量的销售导出。能跑通，但伪造数据一旦变成
月度动作，回写的正确性就挂在假数据上了——故另起 `safety_writeback.py`。

## 用法

```bash
python3 sales_insight/sales_insight.py <销售数据.xlsx> \
    --products <product.product.xlsx> \
    --safety <运营的安全库存表.xlsx>

python3 sales_insight/test_sales_insight.py     # 构造数据测试
```

**导出销售数据时按周分组**（ERP 里筛好日期区间、行维度按周），脚本会从表头数出期间
周数，不用你给 `--weeks`。想只看近四周就导近四周——这正是安全库存该看的口径。

`--weeks` 只在两种情况下用：导出是旧的整期累计格式（没有周信息，此时**必填**），
或你想覆盖自动值（会告警提示与表头不符）。

## 输入

| 文件 | 来源 | 必需 |
|---|---|---|
| 销售数据 | Odoo「Sales Analysis」透视导出。按周分组、整期累计**两种格式都吃**，自动识别 | ✅ |
| 产品主数据 | `product.product` 导出，**必须含 `External ID`**（回写用的唯一映射码） | ✅ |
| 安全库存表 | 运营手工维护 | 可选，但**优先于脚本推算** |

**产品主数据导出时请勾上这几列**，每一列缺了都只是降级、脚本会明确告警，但值得一次勾全：

| 列 | 缺了会怎样 |
|---|---|
| `Quantity On Hand` | 补货提醒只能退回运营表那份日期快照（覆盖有限、会过期） |
| `Supply Remark` | 回写表不带备注列，运营备注进不了 ERP |
| `FS` 或 `Product/FS` | 补货提醒里「去谁家订」为空 |
| `Safety Stock` | 看不到 ERP 现值，无从判断两边是否已同步 |

| 文件 | 内容 |
|---|---|

| `安全库存回写表.xlsx` | `id` / `SKU(勿导入)` / `Safety Stock` / `Supply Remark` → 导入 ERP 产品主数据。**只含运营人工审过的值** |
| `安全库存回写表-试X.xlsx` | 给了试水 SKU 时多出这一份，只含那一条。**先导它**验证，再导上面的全量——全量那份照出不误，不用为拿它再跑一遍 |
| `安全库存候选值.xlsx` | 脚本推算的值，**待运营审阅**。前三列与回写表同头，审完可直接导；只含推算值 >0 的（推算=0 的低销量长尾已剔除，导进去只会把它们刷成 0） |

## 回写表的三处讲究

导入 Odoo 时它**只写文件里出现的列**——但「有列而该格为空」的处理是**把该字段清空**。
所以回写表的每一列，要么是真想改的，要么必须带上原值。由此有三条：

1. **`SKU(勿导入)` 这列纯给人看**，用来在导入后一眼定位「哪个货的安全库存是多少」。
   表头故意不叫 `Internal Reference`——那会被 Odoo 自动映射上，一旦忘了取消勾选就把
   SKU 重写一遍（导出值带 `\t` 前缀，真写回等于改了数据）。现在这个表头 Odoo 认不出，
   导入界面显示为未映射，你不勾它就不会被写。
2. **`Supply Remark` 每一行都带 ERP 现值**。运营备注前置成 `YYYYMMDD:安全库存 …` 段，
   原有内容一律保留在后面；**没有新备注的行原样带回现值**，不留空。留空的话，
   那些产品在 ERP 里已有的备注会被清掉——其中往往就有 `fs_writeback` 写的供应商画像。
3. **重跑不堆叠**。`Supply Remark` 是多方共用的自由文本（运营手写、`fs_writeback` 的
   供应商画像、本脚本的安全库存备注），约定用 `；` 分段、每段以 `YYYYMMDD:<前缀>` 开头，
   各脚本按签名认出自己的旧段替换掉，别人的段和人工原文不动。逻辑在 `common/remark.py`，
   两个脚本共用。已知残留风险：人工备注里若出现 `；` 会被误切成两段。

同一条「Odoo 认不出的表头 = 不会被写」也用在**候选值表**上：它前三列
`id` / `SKU(勿导入)` / `Safety Stock` 与回写表完全一致、直接可导，后面接
`商品名称 / 销量 / 销量排名 / 周均销量 / 在手库存` 作审阅依据——中文表头在导入界面
显示为未映射，不勾就不会被写。**「能直接导」和「审的时候看得到依据」不必二选一。**
候选值表**不带** `Supply Remark`：候选品不在运营安全库存表里、没有运营备注，
带这列只会平白无故重写该字段。

## 关键口径

- **人工值优先，推算值只作候选**。推算 = `期间销量 / 期间周数 × 覆盖周数`（默认 2 周），
  基于**期间均值**，会低估上升期新品、高估下滑品。**未经人审的阈值不许进 ERP 主数据**
  （2026-08-01 用户拍板）。运营审完并入安全库存表，下次跑就自动走「运营人工」并进回写表。
- **推算口径自检**：脚本会拿运营已给的值反过来对，报出「推算值与人工值偏差在 ±50% 以内
  的占比」和中位偏差。偏差大说明 `--weeks` / `--cover-weeks` 给得不对，或该品趋势变化大。
- **「订购频率 / 每次订购数量」**= `# of Lines`（被下单次数）与 `Qty Ordered / # of Lines`。
  实测**几乎全是 1.0**（B2C 一单一件），此指标在这门生意里信息量很低，真正有用的是销量
  排名 + 周趋势。留着是因为最初需求点名要，但别指望它。

## 三个解析坑（不处理就一条都对不上）

1. **`product.product` 的 `Internal Reference` 前面带 `\t` 制表符**（Odoo 强制 Excel 按文本
   处理），不 `strip()` 连接率是 0。
2. **销售透视表的商品名前面有缩进空格**（`    [SKU] 名称`），正则写 `^\[` 匹配不到，
   必须 `^\s*\[`。
3. **按周分组的导出里，某周没卖是空格而不是 0**。当缺失跳过的话「近4周均销」会被算高
   （拿 3 周的和除以 3），必须填 0 再参与均值。

另外销售导出的结构随「行维度是否按周」而变，脚本以「首列 == `Total` 的那一行」为锚
自动定位：它上面一行是 `Untaxed Total / # of Lines / Qty Ordered` 子表头，再上一行若带
`W28 2026` 这样的标签就是周分组行；列从第 1 列起每 3 列一组，**带周标签的是周分组，
不带的那组是整期合计**——销售额/销量一律取合计组。旧的 4 列格式即「只有一组、且它就是
合计组」，天然兼容。脚本会拿明细求和与 Total 行对拍，解析错了立刻暴露。

⚠ 这里踩过一次：新导出有 16 列，旧解析硬读前 4 列，会**静默把 W28 一周的数当成整期**
——比报错更糟。所以才改成按表头认而不是按列位置认。

安全库存表的在手库存列名带日期前缀（`7.29在手库存`、下个月是 `8.31在手库存`），
按「包含"在手库存"」匹配而非写死列名。

## `safety_writeback.py` — 运营的表直接出回写表（2026-09-22 起）

```bash
python3 sales_insight/safety_writeback.py <安全库存表.xlsx> \
    --products <product.product.xlsx> [--col 15天安全库存] [--test-sku <SKU>]

python3 sales_insight/test_safety_writeback.py     # 构造数据测试
```

GUI 里是「安全库存直写」标签页，与「销售分析 · 安全库存」并列，共用同一份产品主数据。

### 产出

| 文件 | 内容 |
|---|---|
| `安全库存回写表.xlsx` | `id` / `SKU(勿导入)` / `Safety Stock` → 导入 ERP。**三列，没有 `Supply Remark`** |
| `回写核对表.xlsx` | SKU / 商品名称 / 供应商FS / ERP现有安全库存 / 将写入 / 变化 / 在手库存 / 缺口。**导入前对着它过一遍** |
| `未匹配SKU.xlsx` | 对不上产品主数据的 SKU（有才出）。这些**不会被写入** |
| `安全库存回写表-试X.xlsx` + `导入前快照-X.xlsx` | 给了 `--test-sku` 时多出这两份 |

### 对产品主数据的要求：只有两列是必需的

写入本身只用 `External ID`（映射码）+ `Internal Reference`（SKU 匹配），**缺了直接报错**。
其余各列只服务于「导入前后你怎么核对」，缺了一律只降级、不中断：

| 列 | 进回写表? | 实际用途 | 缺了会怎样 |
|---|---|---|---|
| `External ID` / `Internal Reference` | ✅ | `id` 列 / SKU 匹配 | 报错，跑不了 |
| `Safety Stock` | ❌ | 核对表的「ERP现有安全库存 / 变化」+ 摘要的「新写入 / 无变化 / 有变动」计数 | 回写表照出，核对表那两列全空 |
| `Quantity On Hand` | ❌ | 核对表的「在手库存 / 缺口」 | 同上 |
| `Name` / `FS` | ❌ | 核对表可读性 | 核对表只剩 SKU |
| `Supply Remark` | ❌ | **只进 `--test-sku` 的导入前快照** | 快照少一列 |

顶层 README 那句「三条回写吃同一份产品主数据、列请勾全」是按三条流水线的并集说的。
单跑本脚本时，**`Safety Stock` 值得勾**——没有它，核对表就退化成一张「将写入」清单，
看不出哪些行其实没变化、哪些变动幅度大得可疑（如 5 → 120，可能是运营填错了行），
等于没得核对。`Supply Remark` 则**不必为本脚本重导**：本脚本压根不写这个字段，
唯一用处是首次试水时快照里带着它，导入后对比一次、实证它没被动过。

### 为什么不带 `Supply Remark`（2026-09-22 用户拍板）

运营这类需求表只有数值、没有备注列，**没有任何新内容要写进这个字段**。列整个不出现，
Odoo 就完全不碰它，`fs_writeback` 写的供应商画像与人工原文零风险。同一条理由在候选值表
上已经用过一次（见上文「回写表的三处讲究」）。

代价是 ERP 里若残留 `sales_insight` 早先写的 `YYYYMMDD:安全库存 …` 段，日期会显得过时。
刻意接受：**过时的备注只是难看，被清空的供应商画像是真丢数据。**

### 值列名按「包含」认，命中多个就报错

运营的列名带口径前缀（`15天安全库存`，下次可能是 `10天安全库存`），故按包含匹配——
`sales_insight.read_safety` 要求列名**恰好**是 `安全库存`，认不出这类表。但表里一旦出现
两个含「安全库存」的列，脚本**不替人猜口径**，报错要求 `--col` 指定。

### 四条「宁可报错也不出表」

回写表是要导进 ERP 主数据的，多一行、少一行、值歪一位，都比报错难发现得多：

1. **值为 0 / 空 / 负数 / 小数 → 拒绝出表**并报出 Excel 行号。0 导进去是把安全库存**清零**，
   不能混在几十行里悄悄过去。确实要清零加 `--allow-zero`（GUI 里是那个勾选框）。
2. **安全库存表里重复 SKU → 报错**并列出两个值——写哪个不能替人决定。
3. **产品主数据里同一 SKU 多行 → 报错**。`read_products` 是静默 `drop_duplicates(keep="first")`，
   对销售分析无伤大雅，但回写是按 External ID 改主数据，取错那行等于写到另一个产品上，
   导入日志里还看不出异常。2026-09-22 实测那份 10278 行的导出里全局就有 21 个重复 SKU。
4. **SKU 对不上产品主数据 → 不写，单独出表**，并直接指向「导出筛选条件只勾 `can be sold`」。

### 实测（2026-09-22，天猫「9.18安全库存需求反馈」）

52 个 SKU 的 `15天安全库存`（5–120，无 0、无重复、无缺失），拿 7 月那份 10278 行的
产品导出试匹配：**52/52 全中**，目标 SKU 无重复档，回写表 52 条、值与源表逐行一致。

⚠ 这 52 个里有 `Avene_13883685x2` / `DOPH_12351236x2` / `Femibion_15200041_VO` /
`Lactobact_13502016_GW` / `Orthomol_17444652x2` / `Rotbackchen_01346054x2` ——
**正是上文记录的「`VO active=true` 会漏掉的 9 个」里的 6 个**。产品主数据导出的筛选条件
一旦勾错，这 6 个会静默拿不到 ERP ID。这不是理论风险，是这批数据的实际构成。

构造数据测试 28 项全过，覆盖上面四条拒绝、`--col` 指定、试水、以及产品主数据没勾
`Safety Stock`/`Quantity On Hand` 时只降级不中断。
