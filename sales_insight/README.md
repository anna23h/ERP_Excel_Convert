# sales_insight — 销售分析 + 安全库存提醒 + Safety Stock 回写

## 为什么有这条流水线

运营同事在 Excel 里手工维护安全库存；而 **ERP 产品主数据里本来就有 `Safety Stock` 字段，
`vo_orders/build_excel.py` 的「补货预判清单」已经在读它**（连同 `Quantity On Hand` 和 `FS`）。
两边完全断开——运营的判断进不了 ERP，拉单流程拿到的是过期或空的安全库存。

这条流水线把三份数据合一，产出排名与提醒，并**把安全库存写回 ERP**，让已有的补货预判
清单自动拿到正确值。两条流水线就接上了。

## 用法

```bash
python3 sales_insight/sales_insight.py <销售数据.xlsx> \
    --products <product.product.xlsx> \
    --safety <运营的安全库存表.xlsx>

python3 sales_insight/test_sales_insight.py     # 构造数据测试
```

**导出销售数据时按周分组**（ERP 里筛好日期区间、行维度按周），脚本会从表头数出期间
周数，不用你给 `--weeks`。想只看近四周就导近四周——这正是安全库存该看的口径。

`--weeks` 只在两种情况下用：导出是旧的整期累计格式（没有周信息，此时**必填**），
或你想覆盖自动值（会告警提示与表头不符）。

## 输入

| 文件 | 来源 | 必需 |
|---|---|---|
| 销售数据 | Odoo「Sales Analysis」透视导出。按周分组、整期累计**两种格式都吃**，自动识别 | ✅ |
| 产品主数据 | `product.product` 导出，**必须含 `External ID`**（回写用的唯一映射码） | ✅ |
| 安全库存表 | 运营手工维护 | 可选，但**优先于脚本推算** |

**产品主数据导出时请勾上这几列**，每一列缺了都只是降级、脚本会明确告警，但值得一次勾全：

| 列 | 缺了会怎样 |
|---|---|
| `Quantity On Hand` | 补货提醒只能退回运营表那份日期快照（覆盖有限、会过期） |
| `Supply Remark` | 回写表不带备注列，运营备注进不了 ERP |
| `FS` 或 `Product/FS` | 补货提醒里「去谁家订」为空 |
| `Safety Stock` | 看不到 ERP 现值，无从判断两边是否已同步 |

## 产出

| 文件 | 内容 |
|---|---|
| `销量排名.xlsx` | 全 SKU 按销量排序，含累计占比（ABC 分析）、下单次数、每单件数、安全库存及其来源、在手库存及其来源、缺口 |
| `补货提醒.xlsx` | 在手库存 < 安全库存 的 SKU，按缺口降序 |
| `安全库存回写表.xlsx` | `id` / `SKU(勿导入)` / `Safety Stock` / `Supply Remark` → 导入 ERP 产品主数据。**只含运营人工审过的值** |
| `安全库存回写表-试X.xlsx` | 给了试水 SKU 时多出这一份，只含那一条。**先导它**验证，再导上面的全量——全量那份照出不误，不用为拿它再跑一遍 |
| `安全库存候选值.xlsx` | 脚本推算的值，**待运营审阅**。前三列与回写表同头，审完可直接导；只含推算值 >0 的（推算=0 的低销量长尾已剔除，导进去只会把它们刷成 0） |

## 回写表的三处讲究

导入 Odoo 时它**只写文件里出现的列**——但「有列而该格为空」的处理是**把该字段清空**。
所以回写表的每一列，要么是真想改的，要么必须带上原值。由此有三条：

1. **`SKU(勿导入)` 这列纯给人看**，用来在导入后一眼定位「哪个货的安全库存是多少」。
   表头故意不叫 `Internal Reference`——那会被 Odoo 自动映射上，一旦忘了取消勾选就把
   SKU 重写一遍（导出值带 `\t` 前缀，真写回等于改了数据）。现在这个表头 Odoo 认不出，
   导入界面显示为未映射，你不勾它就不会被写。
2. **`Supply Remark` 每一行都带 ERP 现值**。运营备注前置成 `YYYYMMDD:安全库存 …` 段，
   原有内容一律保留在后面；**没有新备注的行原样带回现值**，不留空。留空的话，
   那些产品在 ERP 里已有的备注会被清掉——其中往往就有 `fs_writeback` 写的供应商画像。
3. **重跑不堆叠**。`Supply Remark` 是多方共用的自由文本（运营手写、`fs_writeback` 的
   供应商画像、本脚本的安全库存备注），约定用 `；` 分段、每段以 `YYYYMMDD:<前缀>` 开头，
   各脚本按签名认出自己的旧段替换掉，别人的段和人工原文不动。逻辑在 `common/remark.py`，
   两个脚本共用。已知残留风险：人工备注里若出现 `；` 会被误切成两段。

同一条「Odoo 认不出的表头 = 不会被写」也用在**候选值表**上：它前三列
`id` / `SKU(勿导入)` / `Safety Stock` 与回写表完全一致、直接可导，后面接
`商品名称 / 销量 / 销量排名 / 周均销量 / 在手库存` 作审阅依据——中文表头在导入界面
显示为未映射，不勾就不会被写。**「能直接导」和「审的时候看得到依据」不必二选一。**
候选值表**不带** `Supply Remark`：候选品不在运营安全库存表里、没有运营备注，
带这列只会平白无故重写该字段。

## 关键口径

- **人工值优先，推算值只作候选**。推算 = `期间销量 / 期间周数 × 覆盖周数`（默认 2 周），
  基于**期间均值**，会低估上升期新品、高估下滑品。**未经人审的阈值不许进 ERP 主数据**
  （2026-08-01 用户拍板）。运营审完并入安全库存表，下次跑就自动走「运营人工」并进回写表。
- **推算口径自检**：脚本会拿运营已给的值反过来对，报出「推算值与人工值偏差在 ±50% 以内
  的占比」和中位偏差。偏差大说明 `--weeks` / `--cover-weeks` 给得不对，或该品趋势变化大。
- **「订购频率 / 每次订购数量」**= `# of Lines`（被下单次数）与 `Qty Ordered / # of Lines`。
  实测**几乎全是 1.0**（B2C 一单一件），此指标在这门生意里信息量很低，真正有用的是销量
  排名 + 周趋势。留着是因为最初需求点名要，但别指望它。

## 三个解析坑（不处理就一条都对不上）

1. **`product.product` 的 `Internal Reference` 前面带 `\t` 制表符**（Odoo 强制 Excel 按文本
   处理），不 `strip()` 连接率是 0。
2. **销售透视表的商品名前面有缩进空格**（`    [SKU] 名称`），正则写 `^\[` 匹配不到，
   必须 `^\s*\[`。
3. **按周分组的导出里，某周没卖是空格而不是 0**。当缺失跳过的话「近4周均销」会被算高
   （拿 3 周的和除以 3），必须填 0 再参与均值。

另外销售导出的结构随「行维度是否按周」而变，脚本以「首列 == `Total` 的那一行」为锚
自动定位：它上面一行是 `Untaxed Total / # of Lines / Qty Ordered` 子表头，再上一行若带
`W28 2026` 这样的标签就是周分组行；列从第 1 列起每 3 列一组，**带周标签的是周分组，
不带的那组是整期合计**——销售额/销量一律取合计组。旧的 4 列格式即「只有一组、且它就是
合计组」，天然兼容。脚本会拿明细求和与 Total 行对拍，解析错了立刻暴露。

⚠ 这里踩过一次：新导出有 16 列，旧解析硬读前 4 列，会**静默把 W28 一周的数当成整期**
——比报错更糟。所以才改成按表头认而不是按列位置认。

安全库存表的在手库存列名带日期前缀（`7.29在手库存`、下个月是 `8.31在手库存`），
按「包含"在手库存"」匹配而非写死列名。

## 实测数据

**2026-08-01 · 按周分组导出 W28–W31（近 4 周）+ 完整产品导出（10331 行）**

- 销售 ∩ 产品主数据 **590/590 (100%)**；安全库存表 62 个 SKU 全部连上、全部可回写。
- 前 44 个 SKU 贡献 50% 销量，前 165 个贡献 80%（共 590 个）。
- 全部 590 个 SKU 都有在手库存数据，其中 **191 个低于安全库存**。
- 回写表 62 条：9 条带上运营备注、53 条原样带回 ERP 现值，**0 条会被清空**。
- 候选值 313 条（另有 215 个推算值为 0 的低销量长尾已剔除，528 → 313）。
- 推算口径自检：偏差在 ±50% 以内的占 **89%**，中位偏差 −5 件。
  对比整期 30 周那次只有 65% —— **近四周口径明显更贴合运营的实际判断**，
  这也从数据上支持了「安全库存就该看近四周」。

**2026-08-02 · 首次真正导入 ERP 后的复核**

回写表 62 条已导入。拿导入后的产品导出（`can be sold`，10266 行）对回来：

- 抽查 `Avene_13883685x2`：`Safety Stock` 100 → **80**（= 运营表的值）；
  `Supply Remark` 变成 `20260801:安全库存 前端…；20260429:夏季+法国探物低价…`
  ——运营备注前置了，**人写的 `20260429` 原文原样保住**。
- **重跑不堆叠在真实数据上验证了**：ERP 里已有我们自己写的 `20260801:安全库存 …` 段，
  次日重跑产出 `20260802:安全库存 …；20260429:…`——旧段被**替换**而非堆叠，
  人写的原文仍在。此前这条只有构造数据验过。
- 因此那次跑的摘要显示「8 条带上运营备注」而非 9 条：其中一条 ERP 现值已等于将写入值，
  属于无变化，不是差异。

**2026-08-01 早些时候 · 整期累计导出（本年至 7 月底，`--weeks 30`）**

- 销售 ∩ 产品主数据 1614/1616 (99.9%)；前 49 个 SKU 贡献 50% 销量（共 1616 个）。
- 运营维护的 62 个 SKU 里 34 个已低于安全库存。
